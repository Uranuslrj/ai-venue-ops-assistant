# 剧本杀门店 AI 运营系统
# 数据表完整设计说明 V1

## 一、系统目标

系统用于帮助剧本杀门店完成：

1. 管理DM基础资料和可用时间；
2. 管理剧本、房间和设备要求；
3. 根据玩家需求匹配合适DM；
4. 记录玩家对DM的六维评价；
5. 通过AI分析文字反馈中的具体问题；
6. 聚合近期同类问题并生成DM改进建议；
7. 由客服或店长发送建议，并跟踪后续改进。

第一版的核心原则：

```text
系统推荐，人工确认；
AI分析，人工复核；
评分及时更新，改进建议按问题聚合后触发。
```

当前使用 CSV 文件作为“文件型数据库原型”，后续可以迁移到 SQLite 或正式业务数据库。

---

## 二、整体数据流

```text
剧本资料
    ↓
场次信息 ← 玩家需求权重
    ↓
DM资料档案
    ↓
硬性条件筛选
    ↓
六维匹配分计算
    ↓
评分可信度修正
    ↓
DM推荐结果
    ↓
场次完成后收集玩家评价
    ↓
AI识别问题、证据和建议
    ↓
聚合同一DM近30天同类问题
    ↓
店长人工重新评级
    ↓
达到阈值后生成改进建议
    ↓
客服/店长发送给DM
    ↓
后续评价验证改进效果
```

# 三、表一：DM资料档案表

对应文件：`dm_profile_template.csv`

## 1. 作用

记录DM是谁、什么时候可用、能主持哪些剧本，以及在六个能力维度上的当前评分。

它是DM推荐系统的基础档案。

## 2. 字段说明

| 字段 | 含义 | 示例 | 类型 |
|---|---|---|---|
| `dm_id` | DM唯一编号 | `DM001` | 主键 |
| `dm_name` | DM姓名或昵称 | 林川 | 文本 |
| `employment_type` | 用工类型 | 全职、兼职 | 枚举 |
| `available_status` | 当前是否可排班 | 可用、不可用 | 枚举 |
| `available_days` | 可工作日期 | 周五、周六 | 文本 |
| `available_time_slots` | 可工作时间段 | 14:00-18:00 | 文本 |
| `hostable_scripts` | 可以主持的剧本 | 诡影山庄、长夜将明 | 文本 |
| `script_types` | 擅长剧本类型 | 欢乐、机制 | 文本 |
| `rule_explanation` | 规则讲解评分 | 4.3 | 数值，1-5 |
| `script_pace` | 剧本节奏评分 | 4.1 | 数值，1-5 |
| `humor_comedy` | 幽默搞笑评分 | 4.5 | 数值，1-5 |
| `performance_immersion` | 演绎沉浸评分 | 4.0 | 数值，1-5 |
| `on_site_adaptability` | 控场应变评分 | 4.2 | 数值，1-5 |
| `service_attitude` | 服务态度评分 | 4.6 | 数值，1-5 |
| `total_review_count` | 历史评价总数 | 18 | 整数 |
| `last_30d_review_count` | 近30天评价数 | 6 | 整数 |
| `default_score` | 无评价时使用的默认分 | 4.0 | 数值 |
| `smoothing_k` | 平滑参数 | 5 | 数值 |
| `notes` | 其他运营备注 | 适合新手车 | 文本 |

## 3. 使用逻辑

系统先根据可用状态、日期、时间和可主持剧本进行硬性筛选，再使用六维评分计算匹配分。

评分次数较少时，使用刷新评分减少偶然高分影响：

```text
刷新评分 =
（历史评分总和 + 系统默认分 × 平滑参数）
÷
（评价次数 + 平滑参数）
```

当评价次数为0时：

```text
刷新评分 = 系统默认分
评分可信度 = 0.75
```

# 四、表二：玩家需求权重表

对应文件：`player_requirement_weights.csv`

## 1. 作用

记录本场玩家更看重DM的哪些能力。

DM资料表回答“这个DM擅长什么”，玩家需求表回答“这一场玩家需要什么”。

## 2. 字段说明

| 字段 | 含义 | 示例 |
|---|---|---|
| `request_id` | 本次玩家需求编号 | `REQ001` |
| `scenario_name` | 场景名称 | 新手欢乐车 |
| `script_name` | 本场剧本 | 诡影山庄 |
| `session_date` | 场次日期 | 2026-09-06 |
| `session_time` | 场次时间 | 19:00 |
| `player_count` | 玩家人数 | 6 |
| `player_type` | 玩家类型 | 新手玩家 |
| `rule_explanation_weight` | 规则讲解权重 | 0.20 |
| `script_pace_weight` | 剧本节奏权重 | 0.15 |
| `humor_comedy_weight` | 幽默搞笑权重 | 0.30 |
| `performance_immersion_weight` | 演绎沉浸权重 | 0.10 |
| `on_site_adaptability_weight` | 控场应变权重 | 0.10 |
| `service_attitude_weight` | 服务态度权重 | 0.15 |
| `total_weight` | 权重总和 | 1.00 |
| `priority_note` | 设置理由 | 新手更需要规则讲解和气氛 |

## 3. 数据规则

六项权重必须合计为 `1.00`。

可以使用预设：

- 欢乐本：幽默搞笑、控场应变较高；
- 情感本：演绎沉浸、幽默搞笑、控场应变较高；
- 推理本：规则讲解、剧本节奏较高；
- 恐怖本：演绎沉浸、控场应变较高；
- 机制本：规则讲解、剧本节奏、控场应变较高；
- 玩家明确提出偏好时，允许人工调整。

# 七、表五：玩家评价表

对应文件：`feedback_records.csv`

## 1. 作用

记录玩家对本场DM的六维评价和具体文字反馈。

这是系统的原始反馈数据，不能直接被AI改写覆盖。

## 2. 字段说明

| 字段 | 含义 | 示例 |
|---|---|---|
| `feedback_id` | 评价唯一编号 | FB001 |
| `session_id` | 对应场次编号 | SES006 |
| `dm_id` | 被评价DM编号 | DM001 |
| `player_id` | 玩家匿名编号 | P001 |
| `submitted_at` | 提交时间 | 2026-09-09 23:20 |
| `rule_explanation_rating` | 规则讲解评分 | 5 |
| `script_pace_rating` | 剧本节奏评分 | 4 |
| `humor_comedy_rating` | 幽默搞笑评分 | 5 |
| `performance_immersion_rating` | 演绎沉浸评分 | 4 |
| `on_site_adaptability_rating` | 控场应变评分 | 4 |
| `service_attitude_rating` | 服务态度评分 | 5 |
| `comment_text` | 文字评价 | 规则讲得很清楚 |

## 3. 关于复购意愿

第一版不使用“是否愿意复购”作为评价字段或推荐依据。

原因是店内评价存在礼貌性表达，玩家可能为了给DM面子而选择“愿意”，参考性不足。

未来如果接入真实订单、会员记录或再次预约数据，可以把真实复购行为作为辅助指标。

## 4. 公平性要求

- 由客服在场次结束后发送评价；
- DM不能查看玩家身份；
- 同一玩家对同一场次只能评价一次；
- 建议设置结束后2-24小时的评价窗口；
- 评分先用于计算，文字问题进入AI分析和人工复核。

# 八、表六：DM推荐结果表

对应文件：`recommendation_records.csv`

## 1. 作用

保存系统针对某个场次生成的DM候选结果、计算分数和推荐理由。

它是一次推荐任务的结果快照，不是DM基础档案。

## 2. 字段说明

| 字段 | 含义 | 示例 |
|---|---|---|
| `recommendation_id` | 推荐记录编号 | REC001 |
| `request_id` | 玩家需求编号 | REQ001 |
| `session_id` | 场次编号 | SES001 |
| `dm_id` | 候选DM编号 | DM001 |
| `dm_name` | 候选DM名称快照 | 林川 |
| `hard_filter_result` | 硬性条件结果 | 通过 |
| `match_score` | 六维匹配分 | 4.25 |
| `review_credibility` | 评分可信度 | 0.955 |
| `final_recommendation_score` | 最终推荐分 | 4.06 |
| `rank` | 排名 | 1 |
| `recommendation_reason` | 推荐理由 | 欢乐和控场维度匹配 |
| `manager_confirmed` | 店长是否确认 | 是、否、待确认 |

## 3. 推荐计算

```text
匹配分 =
DM六维刷新评分 × 玩家六维需求权重之和
```

```text
评分可信度 =
0.75 + 0.25 × 评价次数 ÷（评价次数 + 平滑参数）
```

```text
最终推荐分 =
匹配分 × 评分可信度
```

系统先做硬性筛选，再做软性排序：

```text
可用状态
→ 日期可出勤
→ 时间不冲突
→ 能主持该剧本
→ 六维匹配排序
→ 店长确认
```

# 九、表七：AI评价分析结果表

对应文件：`ai_feedback_results.csv`

## 1. 作用

把玩家的自然语言反馈转成结构化问题、证据、严重程度和改进建议。

这是系统中体现大模型能力的核心环节。

## 2. 字段说明

| 字段 | 含义 | 示例 |
|---|---|---|
| `ai_result_id` | AI分析结果编号 | AI001 |
| `feedback_id` | 来源评价编号 | FB002 |
| `dm_id` | 关联DM编号 | DM001 |
| `issue_dimension` | 问题所属维度 | 剧本节奏 |
| `issue_type` | 具体问题类型 | 中段推进偏慢 |
| `evidence` | 原评价中的证据 | 中段节奏有一点慢 |
| `severity` | AI初始严重程度 | 低、中、高 |
| `suggestions` | AI生成的改进建议 | 设置时间提醒 |
| `ai_status` | AI结果状态 | 待确认、已确认、已驳回 |
| `manager_correction` | 店长修正意见 | 与AI判断一致 |
| `review_window_days` | 评价聚合窗口 | 30 |
| `same_issue_count` | 同类问题累计次数 | 4 |
| `manager_severity` | 店长最终评级 | 低、中、高 |
| `triggered_recommendation` | 是否触发建议 | 是、否 |
| `sent_to_dm` | 是否已发送给DM | 是、否 |
| `sent_at` | 发送时间 | 2026-09-09 23:50 |

## 3. AI处理流程

```text
读取文字评价
→ 判断是否存在具体问题
→ 归入六维能力维度
→ 提取原文证据
→ 判断初始严重程度
→ 生成可执行建议
→ 店长复核
→ 聚合近期同类问题
```

AI不能只输出“表现不好”，而应输出：

```text
问题维度 + 具体问题 + 原文证据 + 严重程度 + 改进动作
```

# 十、表八：DM改进记录表

对应文件：`improvement_records.csv`

## 1. 作用

将已经确认的问题转成可执行的DM改进任务，并跟踪发送、确认和后续复盘。

它负责把“评价”变成“运营动作”。

## 2. 字段说明

| 字段 | 含义 | 示例 |
|---|---|---|
| `improvement_id` | 改进任务编号 | IMP001 |
| `dm_id` | 需要改进的DM | DM001 |
| `issue_dimension` | 问题维度 | 剧本节奏 |
| `issue_type` | 问题类型 | 中段推进偏慢 |
| `source_review_count` | 支持问题的评价数量 | 4 |
| `priority` | 任务优先级 | 低、中、高 |
| `action_owner` | 改进负责人 | DM001 |
| `improvement_action` | 具体改进动作 | 设置阶段时间提醒 |
| `review_period` | 复盘日期或周期 | 未来4场 |
| `status` | 任务状态 | 待执行、观察中、已完成 |
| `result_note` | 复盘结果 | 等待未来评价 |
| `trigger_rule` | 触发规则 | 低严重度累计4次 |
| `manager_reviewed` | 是否店长复核 | 是、否 |
| `sent_by` | 发送人 | 客服、店长 |
| `sent_at` | 发送时间 | 2026-09-09 23:50 |
| `acknowledged_at` | DM确认时间 | 时间或空值 |
| `follow_up_session_count` | 已观察场次数 | 0 |

## 3. 问题聚合和触发规则

统计范围建议为同一DM近30天内的同类问题。

```text
高严重度累计2次
→ 生成改进建议

中严重度累计3次
→ 生成改进建议

低严重度累计4次
→ 生成改进建议
```

未达到阈值时，先进入观察状态。

如果涉及安全、歧视或重大服务失误，店长可以人工升级，单次立即处理。

## 4. 发送和复盘流程

```text
店长复核
→ 达到触发条件
→ 生成改进建议
→ 客服/店长发送给DM
→ DM确认收到
→ 观察未来若干场
→ 比较改进前后的同维度评分和问题次数
```

## 十二、必须区分的三类数据

### 1. 原始事实

例如玩家填写的六维评分和文字评价。

### 2. 系统计算结果

例如匹配分、评分可信度和最终推荐分。

### 3. AI和人工处理结果

例如问题标签、严重程度、改进建议和店长确认结果。

原始事实不能被AI结果覆盖，AI结果也不能绕过人工复核直接影响DM管理。
